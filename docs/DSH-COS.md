# DSH × ContextOS：意识层与执行层的结合


> 读这份当：判断 DSH 宿主能做什么、插件边界在哪。
> 不读这份当 → 版本差异 → `RSI-LEDGER.md`
> DSH = 意识：识别、拆解、编排、验收。
> COS = 身体：工具、存储、界面、网络、可本机可远程。
> 一个任务 = 一个上下文 + 一次契约调用 + 一份可回读的回执。

---

## 一、分工（谁负责什么）

| 层 | 承担 | 不做 |
|---|---|---|
| **DSH（意识）** | 意图识别、目标拆解、计划编排、工具选择、结果验收、经验沉淀 | 不直接改数据、不直接部署、不假装成功 |
| **COS（执行）** | 提供工具（命令契约）、存储（空间/数据）、界面、网络与部署 | 不猜意图、不自行扩大范围 |

契约只有一条：

```
DSH 产出 → { op, args }            （单个或 actions[] 批量）
COS 执行 → { _status, 回读数据, 日志 }
DSH 验收 → 报告 / 反馈 / 下一步
```

插件里已经跑通的形态：`chatWithDSH()` 返回 `{reply, action|actions}`，宿主按 op 分发执行（78 个 op），执行结果回读后进入项目五主体。

## 二、任务生命周期（一个任务一个 COS）

```text
① 识别      DSH 解析意图 → 目标 + 验收判据
② 拆解      目标 → 计划 → 任务（PM 五主体）
③ 配环境    按任务需要 provision 一个 COS：
              本机  → 新建空间（自带仓库/数据/界面）
              远程  → deploy 一个节点（或指定已有节点/空间）
④ 装工具    需要的命令不存在 → 用 COS 的软件工厂现场生成（autogenApp / storeAction）
⑤ 执行      逐条 Action 调用；每条都带上下文（selection/functions）与超时
⑥ 回读验收  200 ≠ 成功；按 append/count/关键字段三件套确认
⑦ 归属      回执写进 报告→反馈；COA 可保留（复用）或回收（释放配额）
```

**关键取舍**：任务与 COS 是 **1:1 可选的**，不是强制的。
- 轻任务：共用当前 COS（省资源）；
- 长任务 / 危险任务 / 需要独立身份的：**独立 COS**（隔离、可回滚、可并行）。

这正好对上 ContextOS 的规模主张：一台设备数百子系统、上万设备互联，正是为了「每个任务都能有自己的执行环境」。

## 三、多智能体协同怎么发生

| 环节 | 机制 | 现状 |
|---|---|---|
| 发现 | UDP 广播 + WS 拨号，见面交换身份/版本/能力 | 源码确认 |
| 寻址 | `Context.Command.Action` 三元组跨设备统一 | 源码确认 |
| 分发 | 目标→计划→任务，天然可切到 N 个 COS 并行 | PM 已实现 |
| 回执 | 报告（做了什么）+ 反馈（结果与教训） | PM 已实现 |
| 收敛 | 任务状态机：process → finished/canceled；反馈 canFinish 才能完成 | 已强制 |
| 隔离 | 一空间一仓库一数据域；跨实例必须带 `place_uid` | 源码确认 |

**协同的本质**：不是「多个模型互相聊天」，而是**多个 COS 各自持有一段可验收的任务**，通过状态机收敛。模型只负责把不确定性变成任务。

## 四、自给自足：工具按需生长

任务的工具缺口有三种处理顺序（与 AGENTS 铁律一致）：

1. **已有能力**：先查 78 个 op 与 COS 上已装应用；
2. **组合已有**：用 `pipeline` / `storeAction` 把现有命令编排成新动作；
3. **现场生成**：`autogenApp` 生成应用模板 → 编译 → 立刻成为新工具（这就是「随时造自己需要的工具」）。

生成出来的工具**留在 COS 里**，下一个任务直接复用——工具随任务增长，而不是随版本发布增长。

## 五、与现状的差距（诚实清单）

| 能力 | 状态 | 缺什么 |
|---|---|---|
| DSH → op 的识别与派发 | 已跑通 | 复杂任务的多次往返、失败重规划 |
| 任务的独立 COS | 手工（部署节点/建空间） | **provisioning API**：`taskProvision({task_uid, mode})` 自动建/绑/回收 |
| 多 COS 并行 | 未实现 | 并发调度、配额、失败隔离 |
| 跨设备寻址 | 契约在，未压测 | 节点注册表、健康探活、路由 |
| 回执与验收 | PM 五主体已实现 | 自动化验收判据（现在靠人/提示词） |
| 回收 | 无 | 任务结束后的空间/节点回收与数据归档 |
| 观测 | 局部（控制台/日志） | 百万级指标、追踪 ID 贯通 |

## 六、分阶段落地

| 阶段 | 交付 | 验收判据 |
|---|---|---|
| **M1 绑定** | `taskProvision`：给任务建/绑 COS，写入任务上下文 | 一条任务能拿到独立空间，`place_uid` 落库 |
| **M2 并行** | 任务级并发执行 + 失败隔离 | 3 个任务并行，任一失败不影响其余，回执齐全 |
| **M3 跨机** | 远程节点纳入任务池（本机/远程同一契约） | 同一条任务在本机与远程各跑一次，结果一致 |
| **M4 自生长** | 工具缺口自动生成并复用 | 任务首次用到不存在的命令 → 自动生成 → 第二次直接命中 |

每一阶段的判据必须机器可判（同 `rsi_loop.py` 的思路），否则又会退化成口号。

---

## 七、风险

1. **成本爆炸**：每个任务一个 COS，若不复用会迅速吃满内存与端口；
2. **编排失控**：模型拆解出无法验收的任务 → 必须先有判据再执行；
3. **回收缺失**：任务结束不释放，百万级立刻变垃圾场；
4. **观测缺失**：没有追踪 ID，跨 COS 的失败无法定位；
5. **安全**：远程节点 + 工具体系意味着高权限，必须默认最小权限与显式确认。
