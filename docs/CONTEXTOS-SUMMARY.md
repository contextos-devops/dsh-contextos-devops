# ContextOS 产品理念 · 工作模式 · 项目规范（插件视角）

> 依据：`CONTEXT.md`（理念/流程/框架）、`AGENTS.md`（铁律/反模式）、本插件 `lib/`（78 个宿主操作）与 `src/client/parts/`（21 个客户端片段）的代码实现。
> 结论标注：**源码确认** / **实测** / **未验证**。

## 一、产品理念

### 1. 一句话

**ContextOS 是云时代的操作系统**：一个 15.2 MB 的静态单文件内核 `bin/ice.bin`，在任意设备上一键部署出完整的私有云，自带运行时、数据层、HTTP、界面引擎、编译链与应用商店——**拷贝即部署，开机即一朵私有云**。

在本插件里，这句话落地为一句产品承诺（聊天首屏原文）：

> One conversation to deploy nodes, create spaces, generate apps, and manage avatars and tasks.
> 一句话部署节点、创建空间、生成应用、管理分身与任务。

### 2. 两条看似相反的根

| 方向 | 含义 | 失守后果 |
|---|---|---|
| **自给自足**（向内） | 代码、工具、数据层、界面、商店全部自造，运行时只依宿主 OS | 断网即停服 |
| **互联互通**（向外） | 节点间直连传播四源（代码/镜像/认证/数据），无中心 | 单机即孤岛 |

顺序是**先自足、再互联**——部署、开发、RSI 的推进顺序都由此而来。

### 3. 三化 × 三通 × RSI（一条因果链）

```text
集群化 → 设备互联互通 → 模块化 → 代码自动生成 → 自动化 → 数据自由流动 → 集群化 …
                                        └→ RSI：自组织、自进化
```

- **横向跨设备**靠集群化：数据离开一台机器；
- **纵向跨应用**靠模块化：数据离开一个应用；
- 两个方向都通，才叫「数据自由流动」。
- **RSI** 是终局：系统自己变强，所以本仓把「七条铁律」做成了可执行判据（`rsi_loop.py`）。

### 4. 一内核 · 三产品 · 两端

| 层 | 是什么 | 落到哪 |
|---|---|---|
| 操作系统 | `ice.bin` 一个文件一朵云 | 节点 |
| 应用平台 | 商店 + 应用单元 + 十朵云 | 空间 `usr/local/work/<space>`、应用 `src/<拼音>/` |
| 智能名片 | toC 身份入口，一人一页 | 小程序三 tab |

两端（小程序 / macOS 客户端）共享同一套 `Context.Command.Action` 契约。

### 5. 概念序（插件的流程条就是它的可视化）

```text
serve（服务节点）→ space（项目空间）→ place（应用实例）→ avatar（数字分身）
→ scene（赛博世界）→ mode（工作模式）→ view（视图模式）→ web（网页）→ editor（源码）
```

别名表由 `lib/core/copilot.js` 的 prompt 固化：节点=serve、空间=space、应用实例=place、分身=avatar、赛博世界=scene、工作模式=mode(factory/avatar/iot)、视图=view(chat/manage/dev)。

## 二、工作模式（三种，边界清晰）

模式不是皮肤，是**权限与能力的开关**（`CHAT_MODES` + host prompt 的硬约束）。

### 1. 软件工厂 `factory`

**做**：部署服务节点 → 创建项目空间 → 生成应用模板 → 生成应用代码 → 编译上线 → 项目五主体。
**典型话术**：`部署服务节点 :9198` / `创建项目空间 demo` / `生成应用模板「员工管理」` / `生成应用代码「员工管理」` / `编译并上线「员工管理」`。
**代码**：`deployNode`、`createSpace`、`officialSpaces`、`autogenApp`、`createApp`、`compile`、`pipeline`。

### 2. 数字分身 `avatar`

**做**：只以当前分身身份（`user.uid`/城市/公司）创建应用实例、添加数据、查看应用数据、拆解目标。
**不做**：不部署节点、不创建空间、不生成代码——这是硬边界。
**代码**：`createInstance`、`writeData`/`readData`、`planProject`；prompt 明写 "never deploy node / create space / generate code"。

### 3. 赛博世界 `iot`

**做**：扫描周边设备（蓝牙/WiFi）→ 连接 → 控制（音量、静音、剪贴板、截图、打开、WiFi、睡眠、锁屏、壁纸、快捷键），以及切换赛博场景与背景。
**代码**：`discoverDevices`、`sysControl`、`createBackground`/`setBackground`。
**约束**：睡眠/锁屏前必须询问。

### 4. 跨模式的项目状态机（门禁）

```text
目标 → 计划 → 任务 → 报告 → 反馈
plan 到 process   才能 taskCreate
task 到 process   才能 reportCreate
feedback canFinish 才能 task finish
任务 finished/canceled 后，报告不能再创建反馈（本插件已强制）
```

## 三、项目规范

### 1. 目录与模块

- **目录即边界**：`usr/local/work/<space>/src/<应用拼音>/`，一应用一目录；模块内一功能一文件。
- **工作空间**是独立 Git 仓库；`bin/var/usr` 不进 Git。
- 节点与空间都是 Git，**版本 = commit/tag**，不另造版本号。

### 2. 接口四方法（方法门）

| 动作 | 方法 |
|---|---|
| create / insert | **PUT** |
| modify / update | **POST** |
| remove / delete / trash | **DELETE** |
| 其余（run/list/…） | POST |

`GET /…/action/…` 一律 405（login/run/command 除外）。

### 3. 报文与校验

- 四键报文：`0x01/0x02/0x03/0x04`（args / option / data / …），按键 `0x0`—`0x4` 解读；
- **200 ≠ 成功**：必须回读（`append` 解析、`count`、关键字段三件套）；
- 值里禁止半角 `/`（服务端会重新切分，200 但写丢）。

### 4. 表单取值（本插件已固化）

1. 取值范围来自 `fieldOptions`；
2. **提交 `value`**，不提交 `name`/`label`（如反馈状态 `canFinish` 要发 `"0"`）；
3. 默认值 = `options[0].value`；
4. 存量数据按 `value/name/label` 三态归一（`optionValue()` 已带缓存）。

### 5. 修改请求的路径规则

- 路径里只放**表单里真实存在的字段**；
- `*_uid` 结尾的字段走**查询参数**（`splitFields()`）；
- 按类型白名单取字段（`PM_FIELDS`），计划不会带报告/反馈的字段。

### 6. 工程纪律（本插件自身）

- `client.js` 是构建产物：改 `src/client/parts/*.js` → `node build/client.mjs`；
- 每次构建 gate（哈希/语法/CSS 版本/布局约束）+ ui-check 72 + i18n + context；
- **可用性门禁** `npm run release`：真的开浏览器、进插件、量尺寸、截图，exit 0 才算完成；
- 设计系统单源：字号 10/12/14、图标 14/18、栏内边距 10、控件 28。

### 7. 反模式（精选）

| 症状 | 正确做法 |
|---|---|
| 看到 200 就当成功 | 状态码 + 长度 + 关键字段 + 回读 |
| 用 GET 调 /action/ | 方法门 |
| 拿 create「探接口」 | 会真建数据；判活只用 `/c/version`、`/c/dream` |
| 改完 go 就以为生效 | 调 `vimer/action/compile` 并查 warn/catch/error |
| 源码写死 `/Users/xxx` | 一律 `CTX_ROOT` 派生 |
| 整份文档丢给 AI | 引用带锚点：`SPEC-CODE.md §2.2` |

### 与理念的对应

- **自足**：插件自己起 PTY、自己读 Git、自己渲染 xterm/Monaco，不依赖外部服务；
- **互联**：同一份 `Context.Command.Action` 既能被终端敲，也能被聊天触发，还能被小程序调用；
- **自动化**：`planProject` 一次把目标拆成 目标→计划→任务→报告→反馈 并逐级推进状态。

## 六、为什么必须这么小：规模与群控（战略意图）

> 这一节来自产品负责人对定位的口述，是本项目所有取舍的**第一性原因**。

### 1. 规模推演

| 层 | 数量级 | 说明 |
|---|---|---|
| 一台设备 | 数百个**子系统** | 一个空间 = 一个子系统（独立仓库、独立数据、独立界面） |
| 一个集群 | 成千上万台设备互联 | UDP 广播发现 + WebSocket 点对点拨号，无中心 |
| 全网 | **几百万个子系统** | 1000 台 × 300 = 30 万；1 万台 × 300 = 300 万 |
| 智能体 | **几百万个** | 一个子系统承载一个智能体（或一组），即可组成多智能体协同网络 |
| 群控 | 无人机 / 机器人 | 同一套「发现 → 指令 → 回执 → 收敛」机制，只是执行器从软件换成硬件 |

**为什么内核要 15.2 MB 单文件**：只有足够小，才能「拷贝即部署」到每一台设备、每一个边缘盒子、每一台机器人；只有零外部依赖，才能在断网现场自足运行；只有单进程内多子系统，才能在一台机器上开出几百个而不炸内存。

### 2. 百万级子系统对架构的硬要求

| 要求 | 机制 | 现状 |
|---|---|---|
| 秒级发现 | UDP 局域网广播 + WS 拨号 | 源码确认（`base/tcp/broad.go`、`base/web/space.go`） |
| 统一寻址 | `Context.Command.Action` 三元组，跨设备同一契约 | 源码确认（插件 78 个 op 均走此契约） |
| 指令下发与回执 | 四键报文 + `_status` + 回读 | 源码确认；百万级压测**未验证** |
| 状态收敛 | 项目五主体（目标→计划→任务→报告→反馈）作为分发与验收骨架 | 插件已实现并实测 |
| 限流与退避 | 调用超时、重连退避、缓存（`optionValue`、`USER_CACHE`） | 局部实现；全局配额**未验证** |
| 隔离 | 一空间一仓库一数据域 + `place_uid` 条件查询 | 源码确认（跨实例读写需显式带条件） |

### 3. 群控 = 多智能体协同

- **每个子系统一个 agent**：agent 的「身体」是空间里的应用与数据，agent 的「动作」是命令契约里的 op；
- **目标分发**：一条目标 → 计划 → 任务，天然可拆到 N 个子系统并行执行，报告/反馈就是执行回执与验收；
- **自组织**：节点见面即交换身份/版本/能力（四源传播），不需要中心编排器；
- **自进化（RSI）**：七条铁律被做成可执行判据（`rsi_loop.py`），百万级系统靠**机器可判**而不是靠人盯。

### 4. 这条战略对工程的直接约束

1. **任何新增能力必须先回答「它会不会让内核变大」**——能放应用层就不进内核；
2. **任何跨设备动作必须走统一契约**，否则百万级无法编排；
3. **任何状态必须可回读**，否则群控无法收敛；
4. **任何流程必须可判据化**，否则 RSI 无法自动化。

### 5. 诚实缺口

- 百万级子系统的**调度、观测、配额、灰度**尚无实现与压测；
- 设备群控目前只到「发现 + 单点控制」（`discoverDevices` / `sysControl`），**批量下发与编队**未实现；
- 上述是方向而非现状——写在这里，避免把愿景当成已交付能力。
